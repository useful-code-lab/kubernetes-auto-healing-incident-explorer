# 🚀 Kubernetes Auto-Healing & Incident Explorer

Инструмент для **автоматического обнаружения, диагностики и устранения проблем в Kubernetes-кластере**.

Проект помогает увидеть, **почему Pod'ы падают, что происходит с приложением и какую реакцию можно выполнить автоматически**, не разбирая каждый инцидент вручную.

Он объединяет в одном инструменте:

* 🔎 обнаружение проблем с Pod
* 🧠 анализ логов и причин сбоев
* 📋 сбор Kubernetes Events
* 📈 метрики для Prometheus
* ⚡ автоматическое масштабирование
* 🩹 self-healing нестабильных Pod
* 👀 наблюдение за состоянием кластера в реальном времени

---

# 💡 Что вы получаете от проекта

Если в Kubernetes-приложении периодически появляются рестарты, падения или нестабильные Pod, обычно приходится вручную:

1. искать проблемный Pod;
2. смотреть количество рестартов;
3. изучать `kubectl logs`;
4. проверять предыдущие логи контейнера;
5. искать Kubernetes Events;
6. определять причину ошибки;
7. решать, нужно ли масштабирование;
8. перезапускать или удалять проблемный Pod;
9. проверять, восстановилась ли система.

Этот проект автоматизирует значительную часть такого процесса.

### Вместо:

```text
Pod упал
   ↓
kubectl get pods
   ↓
kubectl logs
   ↓
kubectl describe pod
   ↓
поиск причины
   ↓
ручное решение
```

можно получить:

```text
Pod упал
   ↓
Explorer обнаружил инцидент
   ↓
собрал логи + Events
   ↓
определил возможную причину
   ↓
зафиксировал метрику
   ↓
при необходимости масштабировал
   ↓
при критической нестабильности удалил Pod
   ↓
Kubernetes создал новый Pod
```

# 🔎 Какие проблемы он помогает обнаруживать

Explorer отслеживает состояние Pod и реагирует на изменения.

Например:

```text
RestartCount: 1 → 2
```

означает, что контейнер был перезапущен.

Проект фиксирует такой случай как инцидент и собирает дополнительную информацию для диагностики.

Также можно обнаружить состояния вроде:

* `CrashLoopBackOff`
* `ImagePullBackOff`
* повторные рестарты контейнера
* неуспешное завершение контейнера
* нестабильные Pod

# 🧠 Автоматический анализ причины сбоя

После обнаружения инцидента Explorer получает информацию из Kubernetes и анализирует логи контейнера.

Например:

| Найденная ошибка     | Возможная причина               |
| -------------------- | ------------------------------- |
| `out of memory`      | OOM / нехватка памяти           |
| `panic`              | аварийное завершение приложения |
| `connection refused` | проблема соединения             |
| `permission denied`  | проблема с правами              |
| `exit code 137`      | завершение процесса из-за OOM   |

Это не полноценная система AIOps и не заменяет глубокий анализ логов.

Задача механизма — **быстро дать первоначальную диагностику**, чтобы сократить время поиска причины.

# 📋 Информация об инциденте

При обнаружении проблемы формируется структурированный отчет:

```text
🔥 INCIDENT

Pod: default/app-123
Restarts: 1 → 2

💀 LAST TERMINATION
Exit Code: 137

📄 LOGS
...

📡 EVENTS
...

🧠 ANALYSIS
Possible cause: OOMKilled
```

Таким образом, вместо просмотра нескольких Kubernetes-команд информация о проблеме собирается в одном месте.

# ⚡ Автоматическое масштабирование

Проект может реагировать на повторяющиеся проблемы с Pod.

Если количество рестартов превышает заданный порог:

```text
RestartCount > 3
```

Explorer пытается увеличить количество реплик Deployment.

При этом используются ограничения:

* максимальное количество реплик;
* cooldown между операциями;
* проверка состояния Pod;
* исключение некоторых сценариев, например проблем с загрузкой образа.

Пример:

```text
Deployment
replicas: 2

        ↓

частые рестарты

        ↓

Explorer

        ↓

replicas: 3
```

Это демонстрационный механизм автоматической реакции, а не замена production HPA.

---

# 🩹 Self-Healing

Если Pod продолжает постоянно падать:

```text
RestartCount > 10
```

Explorer может удалить нестабильный Pod.

Kubernetes после этого самостоятельно создаст новый Pod, если он управляется Deployment/ReplicaSet.

Получается простой цикл восстановления:

```text
Нестабильный Pod
      ↓
обнаружение
      ↓
удаление
      ↓
Kubernetes создаёт новый Pod
      ↓
новый Pod начинает работу
```

Это позволяет использовать стандартный механизм reconciliation Kubernetes для восстановления приложения.

# 🚀 Быстрый запуск

## 1. Запустить Minikube

```bash
minikube start --driver=docker
```

---

## 2. Собрать Docker-образ

Minikube использует собственный Docker daemon:

```bash
eval $(minikube docker-env)
```

Затем:

```bash
docker build -t kube-source-explorer:latest -f kube-source-explorer/Dockerfile .
```

---

## 3. Настроить RBAC

```bash
kubectl apply -f kube-source-explorer/manifests/rbac.yaml
```

---

## 4. Запустить Explorer

```bash
kubectl apply -f kube-source-explorer/manifests/pod.yaml
```

Проверить состояние:

```bash
kubectl get pod kube-source-explorer
```

Посмотреть логи:

```bash
kubectl logs kube-source-explorer
```

# 🧪 Проверка работы

## Создание падающего контейнера

Можно создать Pod, который сразу завершится с ошибкой:

```bash
kubectl run immediate-fail \
  --image=busybox \
  -- /bin/sh -c "echo 'ERROR'; exit 1"
```

Explorer должен обнаружить изменение состояния и зафиксировать инцидент.

---

## Проверка рестартов

Создадим Deployment с постоянно падающим контейнером:

```bash
kubectl create deployment scaling-demo \
  --image=busybox \
  -- /bin/sh -c "exit 1"
```

Проверим Pod:

```bash
kubectl get pods -l app=scaling-demo
```

При повторных рестартах можно наблюдать работу механизма автоматической реакции.

# ⚠️ Ограничения

Проект предназначен прежде всего для обучения, экспериментов и создания основы для собственного решения.

Текущие ограничения:

* состояние хранится только в памяти;
* анализ логов основан на простом поиске строк;
* отсутствует полноценный rate limiting;
* нет долгосрочного хранения истории инцидентов;
* автоматическое масштабирование реализовано как демонстрационный механизм;
* проект не заменяет полноценные production-системы мониторинга и incident management.

```text
Проблема
   ↓

Диагностика
   ↓

   ↓
```
